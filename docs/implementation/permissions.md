## 2. 第一版交付范围

| 模块       | 交付结果                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------- |
| 平台管理   | 查看用户及组织基础信息，封禁／解封普通用户，查看并撤销会话；首位管理员通过受控部署初始化 |
| 组织创建   | 用户自助创建，创建者成为 owner                                                           |
| 预置角色   | 平台维护 `owner / admin / member`，组织内只读，可复制为独立自定义角色                    |
| 自定义角色 | 本组织内创建、修改、删除及分配，资源与操作由平台声明                                     |
| 成员管理   | 每个成员一个角色，按授予边界邀请、调整或移除成员                                         |
| 团队       | 成员分组及协作，一个成员可加入多个团队，不附带团队角色或自动权限                         |
| 所有权     | 每个组织恰有一个 owner；通过原子转让交接，不能并存或缺失                                 |
| 生命周期   | 成员退出后的授权失效、组织归档与恢复、禁用永久删除                                       |
| 权限消费   | Web 页面、菜单、按钮、HTTP、SSR 使用一致的权限语义                                       |

第一版不实现部门树、团队范围授权、多角色分配、平台代用户登录、平台改用户密码或邮箱、界面授予平台管理员、永久删除组织，以及尚未落地的项目／财务等业务角色。小程序和 App 的完整登录适配不属于本计划，但接口和授权实现必须可供未来多端复用。

平台与组织的 `admin` 即使命名相同，也使用独立权限定义和检查入口。浏览器只导入公开、可在客户端使用的权限词表与契约，不导入认证服务端、数据库或 session getter。

## 5. 实施阶段与完成条件

阶段按顺序推进；服务端策略先于管理界面可用，未完成对应策略的能力不得仅依靠前端限制对外开放。

### 阶段 0：核对接口覆盖与现有数据

- 阅读目标包的 `AGENTS.md`，重新核对 Better Auth 锁定版本与实际端点实现。
- 建立组织端点清单：读取、修改、激活组织；成员查询、邀请、接受邀请、角色调整、退出和移除；团队读写；动态角色 CRUD。补充 Admin、oRPC、Server Functions 及直接 `auth.api.*` 调用路径。
- 核对 `organizationHooks`、通用 hooks 和插件扩展是否覆盖各入口；生命周期、授予和返回字段检查必须覆盖直接 HTTP 与服务端调用。
- 核对单一 owner 的原子转让能力：普通成员、邀请、退出、移除和角色调整端点不能创建第二个 owner 或移除当前 owner。
- 用只读方式盘点已有平台角色、组织角色、邀请及团队关系，检查逗号多角色、未知角色、预置名冲突、同组织重复角色、多个 owner 和孤立团队成员关系。

完成条件：形成端点与策略对应清单、模型 diff 预期和存量数据处理清单。不能静默把已有多角色或异常授权降为 member，也不能静默选择多个现有 owner 中的保留者；涉及既有权限变化时先列明影响，再按已授权的数据操作范围处理。

### 阶段 1：权限词表、插件与模型

- 纠正 owner、admin、member 的基础权限；member 不继承管理权限，admin 默认不具有动态角色定义的写权限。
- 按已确认可见范围配置角色定义读取能力；普通成员的“查看自身权限”不能通过开放完整角色管理接口实现。
- 第一版仅声明已实现的组织管理权限。查看基础成员／团队信息按成员资格允许，不能假定 Better Auth 默认提供 `member:read`、`team:read` 等操作。
- 为平台 Admin 单独定义有限权限；除撤销外的会话读取仅用于管理界面，不把会话 token 等凭证返回浏览器。
- 服务端拒绝代登录、改密码、改邮箱、平台角色授予和其他未批准的平台操作，不仅隐藏入口。平台管理员身份变更仅由受控初始化／运维流程执行。
- 启用 `disableOrganizationDeletion`，同时检查 owner 是否可能通过其他入口触发删除。
- 为组织增加服务端受控的归档字段，优先以 `archivedAt` 表达正常／归档状态；普通组织 create/update 输入不能自行写入归档字段或绕过 owner 检查恢复。
- 通过当前版本支持的 CLI 生成认证模型，检查 Admin 字段及组织扩展字段，保留现有关系与必要约束。
- 预置角色仍来自代码，动态角色仍使用 `organizationRole`；不将静态角色按组织复制入库。核对角色唯一性与新增约束对现有数据的影响。

完成条件：服务端与客户端静态权限配置一致，生成模型通过类型及生成流程检查，所有数据库应用步骤尚需遵循第 8 节。

### 阶段 2：服务端授权与生命周期

- 保留请求级 `getSession()`；在认证之后集中校验目标组织的当前成员资格和归档状态，再检查具体权限。
- 使用 Better Auth 支持的权限检查能力读取静态及动态授权，不自行另建角色解析与 Session 系统。允许单请求内复用结果，不依赖跨请求旧缓存实现“下一次请求失效”。
- 角色创建／修改／复制仅允许声明过的资源及操作，授予权限不得超过操作者持有的权限，不能覆盖预置角色名称。
- 创建和分配入口只接受一个角色，拒绝数组多角色及逗号多角色形式；团队数量与单角色分配无关。
- 分别检查角色定义管理和成员角色分配资格，覆盖邀请、接受邀请与角色更新路径，禁止通过邀请迂回授予高权限。
- admin 不得任免其他 admin 或修改自身角色。对权限等同于 admin 的自定义角色同样执行保护，不能通过改名／复制绕过限制；owner 任免与普通角色调整分开处理。
- 修改角色前查询受影响成员数量，实际保存时重新检查当前授权；角色被成员或待处理邀请引用时拒绝删除。
- 每个组织恰有一个 owner；创建组织时由创建者成为 owner，不能邀请或通过普通 add-member／角色更新分配 owner。
- 所有权只能通过显式转让变更：一个原子操作将目标成员设为 owner，并为原 owner 指定一个非 owner 角色。普通退出、移除和角色更新不能变更 owner 身份。
- 转让与成员移除、账号操作并发时，仍须始终恰有一个 owner；检查点必须覆盖锁定与提交边界，不能依赖转让前的读取。
- 如果无法通过已支持的服务端扩展保证此不变量，阻止 owner 变更路径并报告所需的事务或数据库约束，不得以“组织只有一个 owner”替代原子性证明。
- 成员退出／移除后，清理该组织的团队关系。既有会话仍可用于其他组织，下一次目标组织请求必须检查到成员不存在。
- 归档后阻断普通组织读写、团队操作、角色管理、邀请接受、组织激活等入口；仅允许 owner 查看明确受限的归档状态及恢复。归档状态读取与普通组织读取分开授权。
- 所有路径都必须检查归档状态，包括通过邀请 ID、团队 ID、角色 ID 间接定位组织的端点，以及 SSR／Server Functions 的直接服务端调用。
- 同一授权规则覆盖 Better Auth HTTP 与服务端 API。若原生扩展无法保证必要的原子性或策略覆盖，需使用受支持的插件扩展并关闭冲突原入口；不能仅增加一个 oRPC 包装而留下可绕过端点。

完成条件：第 9 节越权、并发、旧会话和归档场景通过。对原子性及直接调用覆盖的技术核查属于实现前置条件，不能用未验证的 hook 行为代替。

### 阶段 3：必要的业务契约与查询输出

在 `packages/api/src/contracts/` 先定义输入、稳定输出 DTO 与预期错误，再实现并汇总 router。以下名称为拟定契约职责，开工时按现有命名统一，不代表已有端点。

| 契约职责               | 输入要点       | 输出与授权                                                          |
| ---------------------- | -------------- | ------------------------------------------------------------------- |
| 组织访问上下文         | 明确 orgId     | 当前用户的成员身份、有效操作能力及组织状态；不返回完整角色管理数据  |
| 归档组织               | orgId          | 仅 owner，状态更新结果                                              |
| 恢复组织               | orgId          | 仅 owner，可在归档状态下执行                                        |
| 查看归档状态           | orgId          | 仅 owner，恢复所需的最小信息                                        |
| 平台组织基础列表       | 分页、搜索条件 | 平台权限，基础信息，不进入租户业务数据                              |
| 受限组织概览／成员查询 | orgId、分页等  | 按当前用户权限限制返回字段；仅在 Better Auth 现有接口无法满足时新增 |

组织访问上下文用于页面预取、菜单和按钮消费动态授权，角色 CRUD 仍复用 Better Auth。不能把聚合接口变成无需认证的全角色导出入口。

重点检查 `getFullOrganization` 和现有组织统计：普通成员不能从网络响应、SSR 预取数据或序列化缓存获得待处理邀请等受限信息。减少返回字段不只发生在前端渲染阶段；若新增受限 DTO，原始直接端点也要实施相同可见范围策略。

完成条件：未知／跨组织资源无法读取，普通成员响应字段受限，契约输出稳定；HTTP 与 SSR 同一处理器行为一致。

### 阶段 4：Web 管理闭环

阶段 4 使用已确认的 [目标路由结构](../architecture/code-organization.md#已确认的目标路由结构)，具体迁移步骤由 [Web 路由重构计划](web-routing.md)维护：共享 `_authenticated` 登录层，个人空间迁移到 `/me`，正常组织业务置于 `_active`，归档恢复页面为兄弟分支；API 独立于页面布局。迁移包含旧 `/dashboard` 子地址的对应重定向。个人收藏业务与资源模型不在本权限计划中提前实现。

| 路由／入口                       | 页面职责                                                |
| -------------------------------- | ------------------------------------------------------- |
| `/admin/users`（新增）           | 用户查询、普通用户封禁／解封及会话管理                  |
| `/admin/organizations`（新增）   | 组织基础信息列表，不能借此进入租户业务数据              |
| `/org/$orgSlug/roles`（新增）    | 预置角色只读、自定义角色 CRUD、复制角色与影响预览       |
| 现有 members 页面                | 单角色选择、邀请、角色分配、成员移除与所有权专门操作    |
| 现有 teams 页面                  | 团队与团队成员，不添加团队授权字段                      |
| 现有 settings 页面               | 按操作权限更新设置，owner 归档入口，移除永久删除入口    |
| `/org/$orgSlug/archived`（新增） | owner 能访问；与 `_active` 并列，不加载正常组织业务数据 |

- `_authenticated` 的 `beforeLoad` 处理登录与有效站内返回地址，组织及 admin 子层各自检查访问资格；已登录无权限显示拒绝访问，邀请流程保持在登录层之外。菜单和按钮消费具体操作权限，不以角色名称代替一般操作权限。
- owner 身份规则仍单独判断。归档恢复路由需与正常组织布局守卫配合，避免 owner 在父路由被阻断后永远无法恢复。
- 改造 `usePermission`，消费服务端预取／查询结果；静态 `checkRolePermission` 不负责数据库中的动态角色。
- 成员角色选择列出预置角色和本组织的可授予自定义角色；服务端始终重新检查可授予性。
- 角色保存显示受影响成员数量；删除时解释阻止原因，提供成员角色调整和邀请处理入口。
- 查询键包含当前用户与 orgId；角色定义／成员角色变更、退出组织、归档／恢复后失效相关权限与业务缓存，并更新路由上下文。
- 退出登录、切换账号清理旧授权缓存；组织切换不能复用其他组织权限。
- 本计划不要求加入实时推送；另一客户端的界面可能暂时保留旧显示，但下一次服务端操作必须按当前权限拒绝并反馈。
- 复用现有 TanStack Query、Form、shadcn / Base UI；改路由源文件，不手工编辑路由生成文件。

完成条件：每项管理行为有等待、成功、失败及无权限反馈，动态角色真实影响页面与操作；完成主站构建及相关访问验证。

### 阶段 5：受控初始化与交付

- 提供后续可审阅的管理员初始化流程，显式指定目标环境与已存在用户；不能把注册规则设成“第一个注册者为管理员”。
- 初始化使用当前插件支持的管理机制，验证幂等性与目标用户；不提供公开 HTTP 初始化入口，不通过界面授予平台管理员。
- 应用部署时关闭所有未批准的 Admin 端点，验证直接请求也被拒绝。
- 记录实际检查、模型应用和存量授权处理结果；同步架构文档中的实现状态。

完成条件：新环境可重复初始化，未授权用户不能成为平台管理员；角色、归档和退出规则经第 9 节验收。

## 6. 实施能力核查与剩余工作

## 7. 存量模型与授权处理

- 普通平台用户保持默认普通身份，不能因启用 Admin 自动成为管理员。
- 现有组织默认保持正常状态；归档字段不得把已有组织意外归档。
- 不把现有普通成员继续继承 admin 权限视为兼容要求；先列明纠正影响，再按确认的矩阵实施。
- 现有动态角色继续使用原组织归属，不自动合并、重命名或删除。角色名称冲突、重复定义、未知权限、多角色成员／邀请需单独列出处理结果。
- `isSystemRole` 不作为唯一保护机制；预置角色来自静态配置。现有字段是否保留通过生成 diff 评估，不顺便进行无关模型清理。
- 清理组织成员关系只影响该组织内的团队关系；未来业务表不得因成员退出级联删除历史记录。

## 8. 数据库与验证执行顺序

以下顺序用于数据库变更交付。owner 锁版本及 Better Auth Teams 缺失字段的迁移已生成，并只在临时 PostgreSQL 容器中验证；未连接或修改任何开发、预发或生产目标。目标数据库仍需按仓库边界单独确认后应用。

1. 在已锁定的 Better Auth 版本上核对 CLI 帮助与生成方式，不使用未核对的 latest 工具升级模型。
2. 完成插件及扩展字段配置后生成模型，检查 schema、关系、索引、默认值和存量数据影响。
3. 提供可审阅 diff；执行前确认具体数据库连接目标和持久化变更范围。
4. 开发环境按 [DB 约定](../../packages/db/AGENTS.md)使用 `vp run db:push`；需迁移交付时使用 `vp run db:generate` 的生成流程并审阅，再在已确认环境执行 `vp run db:migrate`。不手写迁移，不混用未经确认的数据库目标。
5. 运行当前根约定要求的 `vpr check`，检查自动修复范围。
6. 涉及主站、SSR、路由或生成流程时运行 `vp run --filter web build`，并按第 9 节验证。

首次实施需要覆盖明确的权限业务风险；优先为直接端点越权、跨组织访问、唯一 owner 原子转让与并发成员变更、归档绕过建立必要的行为测试，不写仅验证 mock 调用或框架自身的测试。

## 9. 验收场景

验收不能只看按钮隐藏。至少覆盖直接 Better Auth HTTP、oRPC 和适用的 SSR／服务端 API 路径，记录返回行为及数据变化。

| 场景                                                            | 期望结果                                                             |
| --------------------------------------------------------------- | -------------------------------------------------------------------- |
| 未登录访问管理能力                                              | 拒绝，公开接口仍可正常使用                                           |
| 用户创建组织                                                    | 自动成为该组织 owner，无平台管理员身份                               |
| member 直接调用成员／角色／团队管理写接口                       | 拒绝，无持久化变化                                                   |
| member 查询组织、统计及预取数据                                 | 可获取基础信息，响应不包含待处理邀请或完整角色管理数据               |
| 自定义角色获授某项操作                                          | 对应页面和服务端操作可用，未授予操作仍被拒绝                         |
| A 组织成员使用 B 组织 orgId／teamId／roleId／邀请标识           | 拒绝，不读取或修改 B 组织数据                                        |
| 创建同名预置角色、未知资源／操作、多角色输入                    | 拒绝                                                                 |
| 复制预置角色后修改副本                                          | 仅改变副本，不影响原角色或其他组织                                   |
| 管理者创建、分配或通过邀请授予超过自身权限的角色                | 拒绝                                                                 |
| admin 任免其他 admin、修改自己角色或借自定义 admin 等价角色绕过 | 拒绝                                                                 |
| owner 明确委派角色管理能力                                      | 被委派者只能执行授权范围内的角色管理，不能获得 owner 身份            |
| 角色被成员或待处理邀请引用时删除                                | 拒绝，不自动降级成员                                                 |
| 角色权限收回后，另一客户端使用旧缓存继续请求                    | 下一次请求按新权限拒绝                                               |
| 普通邀请、加入、移除、退出或角色更新试图创建／移除 owner        | 拒绝，唯一 owner 保持不变                                            |
| 原子所有权转让                                                  | 目标成为唯一 owner，原 owner 同事务变为指定非 owner 角色；失败时回滚 |
| 并发所有权转让、成员移除或账号操作                              | 始终恰有一个 owner；不能零个或多个                                   |
| 成员移除后使用旧 Cookie／会话访问该组织                         | 下一次请求拒绝；其他组织仍可按原身份访问                             |
| 成员移除                                                        | 该组织团队关系清理，历史业务记录保留                                 |
| 非 owner 归档／恢复组织                                         | 拒绝，包括直接提交归档字段                                           |
| owner 归档组织                                                  | 数据保留，普通业务及直接认证组织端点被限制                           |
| 归档后接受邀请、操作团队、SSR 读取或激活组织                    | 拒绝，不通过间接标识绕过                                             |
| owner 查看归档状态并恢复                                        | 可用，恢复后重新按当前授权访问                                       |
| owner 直接调用永久删除端点                                      | 拒绝                                                                 |
| 普通用户访问平台管理                                            | 拒绝                                                                 |
| 平台管理员代登录、改密码／邮箱或授予平台角色                    | 拒绝，不能只依赖前端入口缺失                                         |
| 平台管理员尝试以平台身份读取租户业务数据                        | 不自动获准，按组织成员与业务规则判断                                 |
| 平台管理员封禁／解封普通用户、撤销会话                          | 经授权可用，实际登录与会话行为符合插件配置                           |
| 初始化重复执行／目标用户不明确                                  | 幂等或明确拒绝，不误授权其他用户                                     |
| 退出登录、切换账号或组织                                        | 不复用其他用户或组织的权限缓存                                       |
