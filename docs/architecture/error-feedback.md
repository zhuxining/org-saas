# 异常反馈设计

本文定义异常从服务端到用户界面的表达方式、职责边界与恢复约束。具体编码规则见 [API 约定](../../packages/api/AGENTS.md)、[Web 约定](../../apps/web/AGENTS.md)和 [Auth 约定](../../packages/auth/AGENTS.md)；实施进度和验证结果不在本文维护。

## 设计目标

异常反馈需要同时满足三个目标：调用方能依据稳定的错误语义决定交互，用户能获得安全且可理解的提示，业务故障能关联到服务端日志。

业务 API、认证接口和页面运行时具有不同的协议与消费方式。系统保留各来源的原生错误表达，通过明确的职责边界保证反馈一致性，避免为展示提示建立另一套跨协议错误模型。

## 职责与协议边界

| 层次           | 职责                                                 | 边界                                                     |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| 业务 API       | 表达预期拒绝、隐藏内部故障细节、关联故障日志         | 使用 oRPC 契约与通用错误码；响应中的文案和详情必须可公开 |
| 认证与组织插件 | 表达认证和标准组织操作的失败                         | 保留 Better Auth 原协议、原因码及预期失败提示            |
| HTTP 接入      | 承接协议请求与响应                                   | 不承担业务错误分类或跨协议转换                           |
| 查询与路由     | 管理请求状态、错误传播和数据恢复                     | 读取失败与页面运行异常交给所属查询、路由或错误边界       |
| 页面与反馈入口 | 根据错误语义、页面状态和操作上下文决定提示与恢复动作 | 按原始契约消费错误；未知异常使用安全兜底提示             |

成功响应使用接口 DTO，错误通过所属协议表达。系统不另建 `AppError` 类型、通用错误码体系或跨协议适配层，不要求各来源返回相同 JSON，也不将 Better Auth 错误转换为 oRPC 错误。

展示职责留在所属入口，是因为同一个错误在首次加载、后台刷新和表单提交中需要不同交互。各入口可以有少量文案重复；只有出现明确的共同职责时才考虑抽取，不以消除重复为由建立全局错误展示协议。

## 业务错误语义

### 预期拒绝

输入不合法、未认证、无权限、资源不存在、状态冲突和限流属于可预期的请求拒绝，分别沿用 oRPC 的 400、401、403、404、409 和 429 语义。调用方依据错误码决定交互，服务端提供可公开的业务提示。

业务错误通常只需要 `code` 和安全的 `message`。只有调用方需要按具体原因采取不同动作时，才在对应领域契约中声明 `data.reason`；仅提示文案不同不足以增加原因码。已有组织原因码由[组织契约](../../packages/api/src/contracts/organization.ts)维护。

错误码和原因码构成程序可判断的语义，提示文本用于向用户解释。调用方不能匹配提示文本来决定业务分支。

### 服务端故障

服务端故障使用适用的 5xx 分类；未知异常使用 500。服务端记录原始异常，对外返回安全提示。堆栈、数据库报错、凭证和上游原始内容不得进入公开响应。

预期 4xx 错误保留原契约详情，不为统一反馈而重建错误。业务 5xx 响应仅额外提供用于排查的 `data.requestId`，不携带内部诊断详情。

这一边界使业务拒绝保留可操作的信息，同时将故障诊断信息限制在服务端。

## 故障关联与排查

业务 API 的请求上下文由服务端生成请求标识。业务故障日志与 5xx 响应中的 `data.requestId` 使用同一标识，前端在能够取得该标识时可将其显示为问题编号。

关联关系为：用户问题编号 → 业务故障响应 → 服务端异常日志。请求标识只用于定位故障，不承担业务原因码或恢复依据的职责。

HTTP 与 SSR 直接业务调用经过相同的业务错误处理边界。SSR 错误向浏览器传播时可能丢失类型或扩展字段；前端不得依赖这些信息始终可用，缺少问题编号时仍需提供完整的兜底反馈。

当前关联范围是业务 API 故障。外部 `x-request-id` 接续、响应头传播和 Better Auth 请求标识接入属于条件性演进，只有出现明确的网关、外部客户端或追踪需求时才扩展。

## 前端反馈与信息安全

反馈入口根据错误来源和当前状态决定展示方式：

| 场景               | 反馈职责                                                         |
| ------------------ | ---------------------------------------------------------------- |
| 业务操作失败       | 页面按原始契约决定交互，需要提示时使用服务端提供的安全文案       |
| 查询首次加载失败   | 由页面或局部反馈承接，避免与全局提示重复                         |
| 已有数据的刷新失败 | 由全局查询提示承接，保留已有数据，展示安全业务文案或固定兜底提示 |
| 通用错误页面       | 展示固定兜底提示；能够取得业务故障编号时附带问题编号             |
| 登录与注册失败     | 认证表单保留预期失败提示，服务端故障和未知异常使用固定兜底提示   |

未知异常的 `message` 不属于可信的公开文案，不能直接展示。程序 `TypeError` 也不能自动解释为断网。无法识别来源或错误语义时，使用“暂时无法完成请求，请稍后重试”等固定提示。

字段校验由现有表单能力承接，服务端校验仍是输入有效性的最终边界。服务端字段错误详情按具体接口需求补充，不提前建立全局 `issues` schema。

## 恢复与重试约束

恢复动作由拥有相关查询或路由状态的入口负责。提供“重试”操作就必须实际重新获取数据，不能只标记缓存失效；失败反馈也不能使已有的可用数据被无谓丢弃。

RPC 传输层不自动重放请求，因为写操作超时并不意味着服务端没有执行，自动重放可能造成重复写入。

读取查询的自动重试属于数据请求策略，由对应查询按场景决定是否重试及等待时间。传输层不重放请求，不要求所有读取查询关闭重试；异常反馈设计也不统一规定 Query 的重试配置。

## 演进原则

扩展错误能力必须由调用方的实际需求驱动：需要不同恢复动作时增加领域原因码，需要字段级反馈时补充对应接口详情，需要跨入口追踪时扩展请求标识传播。扩展仍保留原协议和职责边界，避免把页面展示需求反向变成所有接口必须遵守的新错误协议。
